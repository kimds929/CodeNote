# 스킬: project_supervisor

## 목적
이 스킬은 코드를 대신 만드는 도구가 아니라, **프로젝트별로 “어떻게 개발을 감독할지”를 설계하는 도구**다.
프로젝트 정보, Human의 목표·제약, 사용 가능한 도구를 바탕으로 위험도에 맞는 질문·조사·검증 기준·실행 통제를 구성한다.
그 결과 Coding Agent의 작업을 지시하고 Evidence로 검증하며 상태와 handoff를 관리하는 Supervisor Harness/Package를 생성·검증한다.

## 정의
### 한 문장 정의

`project_supervisor`는 **프로젝트를 분석해 그 프로젝트에 맞는 VibeCoding Supervisor를 설계·조립하는 Meta-Engineering Skill**이다.

### 무엇을 받아서 무엇을 만드는가

```text
입력
= 프로젝트 저장소·문서
  + Human의 목표·성공 기준·제약
  + 사용 가능한 Agent·Tool·검증 환경

판단
= 프로젝트 유형·위험·복잡도·불확실성·가역성 평가
  → 필요한 Supervisor 기능과 통제 수준 선택

출력
= Goal / Evaluation / Authority 계약
  + 프로젝트 맞춤 Workflow·Evidence·Recovery·Handoff 정책
  + 실행 가능한 Supervisor Harness/Package
```

### 역할 경계

| 구성요소 | 하는 일 |
|---|---|
| Generator Skill | 프로젝트를 이해하고 Supervisor Package를 설계·생성·검증한다. |
| Supervisor Runtime | 생성된 Package를 사용해 현재 상태를 관찰하고 다음 작업·검증·handoff를 관리한다. |
| Coding Agent | Supervisor의 지시에 따라 실제 소스 코드를 수정하고 실행·테스트한다. |

### 핵심 용어

- `<REPO_ROOT>`: 감독 대상 프로젝트의 최상위 경로.
- `<SKILL_ROOT>`: 이 `SKILL.md`가 들어 있는 `project_supervisor` 스킬 폴더의 경로.
- `Supervisor Package/Harness`: 프로젝트 목표, 상태, Workflow, 평가 기준, 권한, Evidence, Recovery, handoff 규칙을 담은 감독 운영체계.
- `Evidence`: 테스트 출력, Git 상태, 실행 결과처럼 실제 상태를 확인할 수 있는 관찰 근거.

## GPT 답변
핵심은 첫 답변 이후에 정해진 질문표를 순서대로 묻지 않고, 답변에서 부족한 정보를 찾아 **가장 중요한 질문 하나만 다음에 묻는 방식**입니다.

전체 흐름은 다음과 같습니다.

```text
질문 1: 프로젝트를 자유롭게 설명
        ↓
답변 요약 및 이해 확인
        ↓
확인된 정보 / 추정 정보 / 부족한 정보 구분
        ↓
가장 중요한 부족 정보를 하나 질문
        ↓
답변에 따라 다음 질문을 다시 선택
        ↓
목표·범위·성공 기준·제약·위험·승인 범위가 충분해지면 종료
```

`SKILL.md`에는 다음과 같이 작성하면 좋습니다.

```markdown
### 2.2 `project` Interview

프로젝트 인터뷰는 전문용어를 먼저 요구하지 않고,
Human의 자연어 설명에서 Supervisor 설계에 필요한 정보를 단계적으로 확인하는
Adaptive 질의응답으로 진행한다.

#### 시작 질문

질문 1. 진행하고자 하는 프로젝트에 대해 최대한 자세히 써주세요.

답변에는 다음 내용이 포함될 수 있지만, 반드시 모두 작성할 필요는 없다.

- 무엇을 만들거나 해결하려는지
- 누가 사용하는지
- 현재 어떤 문제가 있는지
- 원하는 결과는 무엇인지
- 이미 가지고 있는 자료나 기존 시스템이 있는지
- 일정, 기술, 비용 등 알고 있는 제약사항

#### 답변 처리 방법

질문 1에 대한 답변을 받은 뒤 다음 순서로 처리한다.

1. Human의 설명을 쉬운 말로 요약한다.
2. 다음 세 가지를 구분한다.
   - Human이 직접 말한 확인된 사실
   - 답변에서 추정한 내용
   - 아직 알 수 없는 내용
3. 요약이 맞는지 확인받는다.
4. Supervisor 설계를 막는 가장 중요한 부족 정보 하나를 골라 질문한다.
5. 답변에 따라 다음 질문을 새로 선택한다.

질문은 한 번에 하나씩만 한다.
이미 Repository나 문서에서 확인한 기술 정보는 반복해서 묻지 않는다.
Human이 모른다고 답하면 억지로 결정하게 하지 말고 미확인 상태로 기록한다.

#### 기본 질문 선택 순서

다음 항목을 모두 묻는 것이 아니라, 답변에 없는 항목만 필요한 순서로 확인한다.

1. 목표
   - 이 프로젝트가 끝났을 때 무엇이 가능해져야 하나요?
2. 대상과 문제
   - 주로 누가 사용하나요?
   - 지금 어떤 불편이나 문제가 있나요?
3. 범위
   - 이번에 반드시 포함할 것은 무엇인가요?
   - 이번에는 하지 않아도 되는 것은 무엇인가요?
4. 성공 기준
   - 어떤 상황이 되면 프로젝트가 잘 끝났다고 판단할 수 있나요?
   - 실제 사용 예시를 하나 들어주실 수 있나요?
5. 우선순위
   - 여러 목표 중 가장 먼저 달성해야 하는 한 가지는 무엇인가요?
6. 제약조건
   - 반드시 지켜야 할 일정, 비용, 기술, 호환성, 개인정보 또는 보안 조건이 있나요?
7. 위험과 금지사항
   - 절대로 망가지거나 발생하면 안 되는 것은 무엇인가요?
8. 승인 범위
   - Agent가 알아서 결정해도 되는 것과 반드시 먼저 확인받아야 하는 것은 무엇인가요?
9. 검증 방법
   - 결과를 무엇으로 확인하면 믿을 수 있을까요? 예: 테스트, 시연, 데이터 비교, Human 검토

#### 답변에 따른 Adaptive 질문

| 답변에서 발견한 상황 | 다음 질문 예시 |
|---|---|
| 목표가 모호함 | 이 프로젝트가 완성되면 누가 무엇을 할 수 있어야 하나요? |
| 사용자가 불명확함 | 이 결과를 가장 자주 사용할 사람은 누구인가요? |
| 기존 프로젝트로 보임 | 현재 잘 작동하는 부분과 바꾸고 싶은 부분은 무엇인가요? |
| 목표가 여러 개임 | 지금 가장 우선해서 해결할 한 가지는 무엇인가요? |
| 성공 기준이 추상적임 | 실제로 어떤 장면이 되면 “완료됐다”고 느끼실까요? |
| DB·데이터·금전·보안·배포가 관련됨 | 절대로 발생하면 안 되는 문제는 무엇인가요? |
| UI 프로젝트로 보임 | 사용자가 처음부터 끝까지 어떤 흐름으로 사용하길 원하나요? |
| AI·연구·실험 프로젝트로 보임 | 무엇을 비교하거나 실험해서 어떤 결론을 얻고 싶나요? |
| 일정이나 제약이 보이지 않음 | 반드시 지켜야 하는 일정이나 환경 조건이 있나요? |
| 승인 기준이 없음 | 어떤 결정은 반드시 Human에게 먼저 확인받아야 하나요? |

#### 질문 선택 우선순위

다음 조건에 해당하는 정보부터 질문한다.

1. 목표나 성공 기준처럼 전체 설계를 결정하는 정보
2. 답이 없으면 작업을 시작할 수 없는 정보
3. 데이터 손실, 보안, 배포 장애처럼 영향이 큰 정보
4. Human의 의도가 여러 방향으로 해석될 수 있는 정보
5. 나머지 세부 정보

#### 인터뷰 종료 조건

다음 정보가 확인되면 추가 질문을 멈춘다.

- 프로젝트 목표
- 작업 범위와 제외 범위
- 성공 또는 수용 기준
- 주요 제약조건
- 절대로 실패하면 안 되는 항목
- 검증 가능한 Evidence
- Human 승인 필요 범위

종료 전에 지금까지의 내용을 요약해 Human에게 확인받는다.
핵심 정보가 없거나 답변이 서로 충돌하면 Supervisor 설계를 진행하지 않고 `HOLD`한다.

#### 산출물

- `HUMAN_INTENT.md`
- `SUCCESS_CRITERIA.md`
- `APPROVAL_BOUNDARIES.md`
- `INTERVIEW_LOG.md`
```

예를 들어 사용자가 “온라인으로 논문을 정리하는 프로그램을 만들고 싶다”고 답하면 바로 `Project Type`, `Risk`, `Complexity`를 묻지 않고 다음처럼 진행합니다.

```text
요약:
논문을 온라인에서 정리하고 관리하는 프로그램을 만들고 싶으신 것으로 이해했습니다.
주 사용자가 본인인지 다른 연구자인지는 아직 확인되지 않았습니다.

질문 2:
이 프로그램을 주로 누가 사용하게 되나요?
```

그리고 사용자가 “제가 혼자 쓰려고 한다”고 답하면:

```text
질문 3:
논문을 정리할 때 현재 가장 불편한 점은 무엇인가요?
```

이처럼 사용자의 일상적인 설명을 먼저 받고, 스킬 내부에서 이를 `Goal`, `Scope`, `Risk`, `Evaluation` 같은 구조화된 정보로 변환하는 방식이 가장 자연스럽습니다.
